# OSPD Phase 3 — GeoLabs Activity Report: Process Profiles Register

2026-09-23 · Gérald Fenoy · GeoLabs SARL · D100 Workflow Profiler / D120 OGC API Processes Profiler

## Summary

On 22–23 September 2026 GeoLabs brought the OSPD process-profiles register (`bblocks-process-profiles`, deliverables D100 Workflow Profiler and D120 OGC API Processes Profiler) from a failing build to a fully validated register whose examples come from real executions of the two reference workflows. Every one of the 13 process profiles is now backed by a `cwltool --provenance` run record of the exact pinned CWL, the register's JSON-LD follows the Wf4Ever and generic-provenance vocabularies, and each profile publishes the engine's own W3C PROV graph. Along the way, five defects were found in the reference packages and toolchain and are reported below for the upstream projects.

## Context

The register holds one OGC Building Block per deployable CWL process of the two OSPD reference workflows: W1 Algae Bloom (CRIM, `crim-ca/ogc-ospd-phase1` at commit `5edd4ec`, 10 profiles across the Earth-Search and Copernicus variants) and W2 KindGrove mangrove biomass (`bblocks-eoap-cct` at `c27c60d`, 3 profiles). Each profile combines an OGC API - Processes `processDescription` derived from the CWL with the `eoap.cct.cwl-to-ogcprocess` transform, an OGC Application Package deploy body, execute and results examples, a provenance view as an instance of the generic provenance profile (`ogc.bbr.provenance.*`), a `wfprov:ProcessRun` record for tools, a process-type register entry (Activity 4) and proposed openEO equivalences.

The processes were selected by the Phase 3 workflow-observability investigation (July–September 2026, three independent observers of ZOO-Project-DRU), whose central result — observability is bounded by a package's decomposition into CWL steps, not by the observing layer — motivates profiling each step as its own building block. That investigation produced the first real run record of W2 (30 July 2026) but no successful end-to-end execution under DRU; the run records used here were obtained directly with cwltool on 23 September.

Toolchain: `_sources/` is generated by `scripts/generate.py` from hand-written `scripts/profiles.yaml` and `scripts/sources.yaml`; the authoritative validation is the OGC `bblocks-postprocess` Docker image (JSON Schema, JSON-LD uplift, SHACL). All work was done on the GeoLabs working copy, validated with that image at every step, and is documented in the repository's `docs/` (`DEVIATIONS.md`, `PROVENANCE-GAPS.md`, `OPEN-QUESTIONS.md`, `VALIDATION.md`) and a contributor `CLAUDE.md`.

## Making the register validate

The first Docker build of the register failed 13 of its 14 building blocks, and every one of the 79 failures was the same check: `**Empty** output Turtle`, which `bblocks-postprocess` treats as a hard error with no opt-out. All JSON Schema validations passed. The cause was structural: no profile had a JSON-LD context, and the context that the tool derives from the OGC API - Processes schemas binds only seven terms (`type`, `minOccurs`, `enum`, …), none of which the examples use at their root, so every snippet uplifted to an empty graph. The one or two snippets per profile that passed did so only because `type` happened to be the single bound term (`[] proc:type "ProcessRun"`), a semantically meaningless triple.

Three fixes were implemented in isolated copies and measured on the real build before choosing:

| Approach | Snippets passing | Blocks passing | Verdict |
| --- | --- | --- | --- |
| A — one `context.jsonld` per profile, `@vocab` re-scoped under `inputs`/`outputs`, `$defs` payloads covered through `x-jsonld-extra-terms` | 102 / 102 | 14 / 14 | retained |
| B — split each profile into one building block per payload (7 blocks for `calculate-band`) | 26 / 102 | 6 / 20 | the OGC API - Processes blocks have no annotations to inherit; better RDF for the provenance and process-type views only |
| C — inline `@context` in the example files | 75 / 102 | 1 / 14 | 13 regressions: `results` schemas use `propertyNames: enum` and reject `@context`; array-rooted `provenance.json` cannot carry one |

Approach A was applied in the generator, not only in the generated files. Two refinements were needed for a clean result: `@vocab` scoped per parameter namespace, because an input literally called `name` was being captured by `dct:title`; and a `base-uri` on every example, without which process identifiers resolved to `file:///workspace/`. The fix also surfaced a data defect: an unquoted comma in a YAML flow mapping of `profiles.yaml` had created a stray key that became an invalid IRI under `@vocab`.

A second pass the next day aligned the context on the upstream vocabularies instead of a local `pp:` mapping: `process-run` examples now uplift to `a wfprov:ProcessRun` with `wfprov:describedByProcess`, `wfprov:usedInput` and `prov:wasAssociatedWith`, and `activityType`/`entityType` become `rdf:type`, as in `ogc.bbr.provenance.provenance`.

## Real run records

Every run-derived example now comes from a real `cwltool --provenance` execution of the exact pinned CWL, not from the 2024 CRIM logs or illustrative placeholders that the register previously used.

**W1 Earth-Search** (23 Sep, 06:26–06:40Z): the pinned `algae-usecase-workflow-earth-search.cwl` against `example/algae-usecase-job-earth-search.yml`, producing 18 outputs across two scattered products (`S2A_29SPC_20190701_1_L2A`, `S2A_29SPC_20190701_0_L2A`). Running it required three deviations, none touching the CWL: build order for the seven Docker images (`base` before the tools, since `docker compose build` does not honour `depends_on`); tagging `ogc-ospd/algae-usecase/reproject-image:latest`, because the CWL pulls an untagged reference while the compose file only builds `:1.0.0`; and, on the arm64 build host, rewriting a dead cross-compilation shebang in conda-forge's `gdal_calc.py` inside the `calculate-band` image. These are documented as `DEVIATIONS.md` U-03–U-05.

**W1 Copernicus** (23 Sep, 07:31–07:34Z): the same package's Copernicus variant, run with Copernicus Data Space S3 credentials, one product (`S2A_MSIL2A_20190701T110621_N0500_R137_T29SPC_20230604T023542`). cwltool redacts the two secret inputs as `(secret-<uuid>)` placeholders throughout the research object — verified in the job order, the PROV entities and the engine log — confirming the register's existing `writeOnly` handling (M-04).

**W2 KindGrove** (23 Sep, 08:01–08:03Z): the register's own pinned CWL (`bblocks-eoap-cct` at `c27c60d`, `mangrove-workflow.cwl#mangrove-workflow`) run with the profile's own execute inputs, superseding an earlier 30-July run of a near-identical but not byte-identical copy of the package.

**What the run records disproved:**

- **M-05** (STAC mapping) was wrong: `mangrove_cli` itself writes a STAC **Catalog** with one Item, not the **Collection** the transform assumed; the profile's output schema rejected the tool's actual output and has been corrected.
- **Q-W1-LOG**: on the shared product, only 2 of 9 Earth-Search checksums and 3 of 9 Copernicus checksums match the 2024 CRIM log; the chlorophyll chain in the 2024 log used different input bands than the pinned CWL, confirming the log predates the pinned commit.
- **Q-W2-DAYSBACK** (new): because KindGrove's `days_back` input is relative to execution time, the identical execute request produced 1.49 ha of mangrove on 30 July and 170.91 ha on 23 September — a result entirely dependent on the calendar date the job happens to run, which the processDescription cannot express.
- **GP-10** (generic provenance gap) is no longer a limitation for these profiles: CWLProv content-addresses every file, so the `execution` bundle now lists one artifact per file inside a Directory output, each with its own checksum, rather than omitting the bundle entirely.

## Register engineering

**Run-record ingestion.** `scripts/generate.py` gained a `load_bag()` reader for CWLProv research objects: it resolves cwltool's naive local `prov:time` against the engine log's UTC timestamps, follows `hadMember` as a top-level PROV-JSON relation (not an entity attribute, a mismatch that silently emptied array-valued outputs on first attempt), and tolerates a missing primary bundle after a failed scatter iteration. `scripts/sources.yaml` gained a `runs:` section naming each research object (`w1-earth-search`, `w1-copernicus`, `w2-pinned`) and, per profile in `scripts/profiles.yaml`, a `run: {prov, step, iteration}` pointer replaces the old CRIM-log lookup entirely — there are no illustrative examples left in the register.

**`scripts/run_workflows.py`** (new) is the local counterpart of a future CI job: it clones the pinned source repositories at their exact commits if absent (refusing to proceed if a present clone has been modified, since `generate.py` itself never downloads anything), builds the W1 images, runs the three workflows sequentially with `cwltool --provenance`, and hands the resulting research objects to the generator. Copernicus credentials are read from environment variables or prompted for interactively (never echoed, never written to the clone); a failed run is preserved as `<bag>-failed-<timestamp>` beside an untouched previous good bag, since `cwltool --provenance` deletes its target directory on start. Tested end-to-end from an empty source directory.

**JSON-LD context.** Beyond the initial fix, the context was aligned on the vocabularies the profiles actually instantiate (`wfprov:*`, `prov:*`) rather than a local `pp:` namespace, and `seeAlso` now links each workflow to its steps and each step back to its parent workflows — a bidirectional relation the register previously omitted entirely, visible in the generated documentation and the viewer.

**Identifier prefix.** Changed from `osc.process-profiles.` (an ungrounded fragment of the incubator's `ogc.osc.` family) to `ospd.process-profiles.`, following the project-root convention already used by `eoap.cct.*`; `ogc.ospd.process-profiles.` remains available as a future incubator-family form. This closed the register's own open question Q-PREFIX.

**Reproducibility.** The full pipeline — clone sources, build W1 images, run the three workflows, regenerate, validate — now runs from a bare machine in two commands (`run_workflows.py --build-images --generate` then `./build.sh`), documented in `README.md` and `CLAUDE.md`, which was substantially rewritten to record every non-obvious decision above for future contributors.

## W3C PROV alignment

The experimental OGC incubator register `ogcincubator/bblocks-prov-jsonld-alt` was evaluated and imported. Each profile now publishes `examples/cwlprov.jsonld`: the CWLProv bundle holding that profile's activity, re-serialised as PROV-JSONLD by the Python `prov` library (≥ 2.0; `generate.py` now requires it), validated against `ogc.ogc-utils.prov.w3c-prov-jsonld`, and — because it is a `.jsonld` snippet — read directly as RDF through its own context rather than the profile's. This is the first example in the register on which the cross-domain-model PROV SHACL shapes evaluate against real focus nodes; every prior provenance example produced only vacuous conformance.

A byproduct of this evaluation: OGC API - Processes Part 5 — Provenance (draft `26-038`) specifies `GET /jobs/{jobId}/prov` with **W3C PROV-JSON as the mandatory default response**, PROV-JSONLD, Turtle, PROV-XML and PROV-N as optional content negotiations, and its own normative fixture is a `cwltool`-produced CWLProv bundle. That draft was not consulted when the JSON-LD-only approach was first chosen; discovering it reverses the priority. The next step, agreed but not yet implemented, is to publish the three formats the register's toolchain can actually validate — PROV-JSON (schema-checked, upstream uplift-suppression issue to be filed for the residual junk triples), PROV-JSONLD (as now), and Turtle (RDF-native, no conversion) — and to omit PROV-N and PROV-XML, for which `bblocks-postprocess` has no validator at all.

Cost measured: the two examples add roughly 1.3 MB to `_sources` and 2–4× to generated documentation page size for the seven W1 tool profiles, which share the largest CWLProv bundle (up to 173 KB per format).

## What the validation actually checks

Each profile's description states that its provenance view is "validated against `ogc.bbr.provenance.provenance`" — a claim worth auditing rather than trusting. Negative testing (deliberately broken documents run through the real schemas and SHACL shapes) showed the wording overstates what happens:

- **Schema.** `ogc.bbr.provenance.provenance` adds no constraint of its own; it is `allOf: [ogc.ogc-utils.prov]`. That upstream schema accepts an activity with no `id`, no `provType`, and an empty provenance array — it only rejects wrong value types or a document carrying no PROV signal at all.
- **SHACL.** The cross-domain-model PROV shapes do find real focus nodes on our graphs (a genuine improvement, see above), but the checks that fire are limited to datatypes: a duplicated `startedAtTime`, a `wasGeneratedBy` pointing at a nonexistent node, a literal value for `used`, or an activity missing its `rdf:type` altogether all still conform.
- **By contrast**, the `ogc.bbr.provenance.execution` bundle (used for W1 workflows and, since the run-record work, W2) is strict: it requires `checksum`, an enumerated `status`, and `engine`, and rejects documents missing any of them.

A tightening was scoped but not yet implemented: a locally profiled `$defs/provenance` requiring exactly one activity with `activityType`, `startedAtTime`, `used` and `qualifiedAssociation.hadPlan`; per-profile SHACL rules targeted at each process-type IRI; and negative test cases in `scripts/validate_offline.py`. OGC API - Processes Part 5's own content requirements (`/req/provenance/prov-content-job-activity`, `-process-entity`, `-input-entity`, `-result-entity`, `-namespaces`, and the recommended `-software-agent`, `-timing`, `-associations`) are the natural basis for that tightening rather than an invented list.

## Open questions and next steps

- **CI automation.** A `run-and-regenerate.yml` GitHub Action (manual dispatch plus a schedule) that runs the three workflows, regenerates, and opens a pull request for review — never auto-commits, since run outputs are date-dependent (Q-W2-DAYSBACK). Not yet written.
- **Part 5 content requirements.** Encode OGC API - Processes Part 5's provenance content requirements as the local schema and SHACL tightening scoped above, rather than an ad hoc constraint set.
- **Splitting the provenance and process-type payloads.** An isolated experiment ("approach B" above) showed that referencing `ogc.bbr.provenance.provenance` and the process-type register at each profile's schema root, instead of bundling every payload under one profile's `$defs`, yields materially better RDF (`oa:hasTarget`, IANA relation types, correct `skos:` typing) for exactly those two views. Not done; would mean one additional building block per profile for each view.
- **A DRU run record.** Every run record obtained this session used `cwltool` directly; no execution under ZOO-Project-DRU / Calrissian has succeeded (consistent with the Phase 3 observability investigation's own finding). W2's `ramMax`/memory finding above is a plausible root cause worth testing directly against DRU.
- **The `bblocks-prov-jsonld-alt` dependency is experimental** (`under-development`, its schema and context reference `openprovenance.org` directly with no local vendoring). A decision is needed on whether to keep tracking it live, pin a commit, or vendor the two schemas into this register.
- **Q-LIC** (licensing, pre-existing, unresolved): the W1 CWL files are referenced under CC-BY-NC-SA-4.0 while this register is Apache-2.0 with attribution; whether the generated processDescriptions' reproduced `label`/`doc` text is acceptable as-is remains an open legal question, not addressed in this session's work.
